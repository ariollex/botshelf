# BotShelf

**BotShelf** — каталог MAX-ботов для бизнеса. Пользователь ищет бота по задаче («счёт», «запись», «клиент»), а не обязан заранее знать точный ник.

Проект доведён до deploy-ready состояния: Go-сервис, PostgreSQL, миграции, защищённая модерация через MAX, адаптивный web/mini-app интерфейс, Docker Compose, HTTPS через Caddy, health/readiness-проверки и тесты.

## Что уже работает

1. Публичный поиск среди опубликованных карточек по названию, нику, описанию и категории.
2. Открытие карточки по ссылке `https://max.ru/<ник>`. Внутри mini-app применяется `WebApp.openMaxLink`, поэтому переход остаётся в MAX.
3. Подача заявки разработчиком. Она не попадает в поиск сразу.
4. Отдельная панель `/admin/` для модераторов. Сервер проверяет подпись `initData` и её срок, а не доверяет `initDataUnsafe` из браузера.
5. Очередь заявок: модератор открывает источник, затем публикует или отклоняет заявку. Опубликованная карточка появляется в поиске сразу.
6. PostgreSQL хранит опубликованные боты, заявки и только SHA-256-хеши временных сессий модераторов.

## Важное ограничение данных

У публичного MAX Bot API нет подтверждённого метода глобального поиска чужих ботов. Поэтому BotShelf не заявляет, что содержит «все боты MAX», и не скрейпит платформу. Это открытый каталог: реальные карточки добавляются владельцами или командой и проходят ручную проверку.

Репозиторий намеренно стартует с **пустым** каталогом: в нём нет фальшивых карточек или несуществующих ссылок. После деплоя модератор добавляет реальные, проверенные карточки через обычную форму.

## Архитектура

```text
MAX (web / mobile)
        │ HTTPS mini-app
        ▼
 Caddy: TLS и reverse proxy
        ▼
 Go HTTP API ── MAX initData HMAC validation
        │
        ▼
 PostgreSQL: bots / submissions / moderator_sessions
```

## Что нужно подготовить один раз

1. VPS с Docker Compose и домен, для которого можно настроить A/AAAA-запись.
2. Бота MAX, к которому затем будет прикреплено mini-app, и его токен.
3. Числовой MAX ID хотя бы одного модератора. Его указывают в `MODERATOR_MAX_USER_IDS`; несколько ID разделяются запятой.

Эти три значения относятся к вашему аккаунту и инфраструктуре, поэтому их нельзя безопасно положить в исходный код.

## Деплой

### 1. Скопировать проект и заполнить секреты

```bash
cd botshelf
cp .env.example .env
openssl rand -hex 32
```

В `.env` укажите:

- `DOMAIN` — ваш публичный домен, например `bots.example.ru`;
- `POSTGRES_PASSWORD` — сгенерированное выше значение (используйте только буквы `a-f` и цифры);
- `MAX_BOT_TOKEN` — токен бота MAX;
- `MODERATOR_MAX_USER_IDS` — числовой ID модератора или список через запятую.

Не публикуйте `.env` и не передавайте токен бота в браузер, презентацию или репозиторий.

### Первый модератор

MAX не показывает числовой ID профиля в обычном интерфейсе, поэтому добавлять значение наугад не нужно. Для первого запуска временно укажите в `.env` заведомо неиспользуемый ID:

```env
MODERATOR_MAX_USER_IDS=9223372036854775807
```

После запуска откройте `https://max.ru/<ник_бота>?startapp=admin`. Панель безопасно покажет **ваш** проверенный MAX ID, но не откроет очередь. Скопируйте этот ID в `.env`, затем перезапустите сервис:

```bash
docker compose up -d
```

После перезапуска снова откройте тот же диплинк — теперь откроется очередь модерации. Для нескольких модераторов укажите ID через запятую, например `123,456`.

### 2. Привязать домен и запустить контейнеры

Создайте A/AAAA-запись `DOMAIN`, указывающую на IP сервера, и убедитесь, что снаружи доступны порты 80 и 443. Затем выполните:

```bash
docker compose up --build -d
docker compose ps
curl -fsS https://<ваш-домен>/readyz
```

`readyz` должен вернуть `{"status":"ready"}`. Caddy сам получает и продлевает TLS-сертификат. Каталог и PostgreSQL наружу не публикуются: доступен только HTTPS-прокси.

### 3. Прикрепить mini-app к боту MAX

В настройках созданного бота укажите `https://<ваш-домен>` как URL mini-app. Откройте бота в мобильном и веб-клиенте MAX. Интерфейс должен открыться одинаково в обоих клиентах.

### 4. Открыть админ-панель и наполнить каталог

1. Отправьте карточку реального бота через форму «Добавить своего бота».
2. Под аккаунтом из `MODERATOR_MAX_USER_IDS` откройте диплинк **того же бота**: `https://max.ru/<ник_бота>?startapp=admin`.
3. Основной mini-app увидит стартовый параметр `admin`, откроет `/admin/` и передаст туда подписанный MAX `initData` только в рамках текущей вкладки.
4. Сервер проверит подпись, дату выдачи и MAX ID. Если всё верно, откроется очередь заявок.
5. Проверьте ник в MAX и официальный источник, затем нажмите «Опубликовать» или «Отклонить».

Диплинк не является секретом и сам по себе не даёт прав: `startapp=admin` выбирает только страницу. Каждое действие с заявкой требует сессии, которую сервер выдаёт только после проверки подписанного `initData` и совпадения ID с `MODERATOR_MAX_USER_IDS`.

Это обязательная ручная часть продукта: без открытого глобального API нельзя честно и безопасно автоматически собрать весь каталог MAX.

## Локальный просмотр

Для просмотра интерфейса не нужен домен, публичный HTTPS или настоящий токен MAX. Локальный Compose поднимет PostgreSQL и Go-сервис, а Caddy выключит:

```bash
cp .env.local.example .env.local
docker compose --env-file .env.local \
  -f compose.yaml -f compose.local.yaml up --build
```

Откройте [http://localhost:8080](http://localhost:8080). Остановить сервисы можно `Ctrl+C`, а удалить локальную базу после эксперимента — `docker compose --env-file .env.local -f compose.yaml -f compose.local.yaml down -v`.

В этом режиме работают поиск, форма заявки и API. Админ-панель намеренно не откроет очередь: MAX выдаёт подписанный `initData` только настоящему mini-app внутри клиента MAX.

## Локальная разработка и проверки

Unit-тесты не требуют базы:

```bash
GOPATH="$PWD/.cache/go-path" \
GOMODCACHE="$PWD/.cache/go-mod" \
GOCACHE="$PWD/.cache/go-build" \
go test ./...

GOPATH="$PWD/.cache/go-path" \
GOMODCACHE="$PWD/.cache/go-mod" \
GOCACHE="$PWD/.cache/go-build" \
go vet ./...
```

Проверяемые свойства тестов:

- неподписанные или просроченные `initData` не дают вход модератора;
- заявка не появляется в поиске до публикации;
- опубликованная заявка появляется в каталоге.

## HTTP API

Полная машиночитаемая спецификация — [openapi.yaml](openapi.yaml). Для чекера хакатона — [DATA-API.yaml](DATA-API.yaml).

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/healthz` | Процесс жив |
| `GET` | `/readyz` | Сервис и PostgreSQL готовы |
| `GET` | `/api/v1/categories` | Категории |
| `GET` | `/api/v1/bots?q=&category=` | Поиск опубликованных карточек |
| `POST` | `/api/v1/submissions` | Отправить заявку |
| `POST` | `/api/v1/auth/max` | Обменить проверенный MAX `initData` на сессию модератора |
| `POST` | `/api/v1/auth/max/identity` | Узнать свой проверенный MAX ID при первичной настройке |
| `GET` | `/api/v1/admin/submissions` | Очередь модерации |
| `POST` | `/api/v1/admin/submissions/{id}/approve` | Опубликовать |
| `POST` | `/api/v1/admin/submissions/{id}/reject` | Отклонить с причиной |

## Структура

```text
cmd/server/                 точка входа и встроенный интерфейс
internal/catalog/           предметная модель, PostgreSQL и миграции
internal/httpapi/           REST-обработчики
internal/maxauth/           проверка подписи MAX initData и сессии
cmd/server/web/admin/       отдельный интерфейс модерации
compose.yaml, Caddyfile     production-развёртывание
```

Официальные источники по интеграции: [подключение mini-app и диплинки](https://dev.max.ru/docs/webapps/introduction) и [серверная проверка `initData`](https://dev.max.ru/docs/webapps/validation).
